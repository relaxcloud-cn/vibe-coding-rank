# AI 判定流程

目标：判断一个人是否能在不亲手写每一行代码的情况下，仍然拥有系统结果。

不要从分数出发。先看封顶条件，再看正向证据，最后给段位。

## 一、输入

优先读取 `prepare_evidence.py` 生成的摘要：

- `evidence_cards`：可用于判断的行为证据卡。
- `weak_signals`：弱信号，只能辅助描述，不能直接升品。
- `rank_caps`：段位封顶原因。
- `rank_gates`：机器可读的段位门槛状态。每个 gate 都包含 `id`、目标 `level`、是否通过、观测值、要求值和原因。复核高段位时先看这个字段。
- `unlock_status`：八品、九品是否解锁。
- `preliminary_rank`：自动初筛结果，只能作为参考。
- `user_control_count`：用户主动控制证据数。六品以上必须看这个字段。
- `usage_stats`：AI 投入强度硬统计。只能解释使用强度，不能用于升品。
- `hard_stats`：客观统计画像，包括 token、活跃天数、会话数、有效样本比例、强证据密度、主动控制占比。只能解释样本质量和使用强度，不能直接抬段位。

## 二、六个判断维度

1. 目标定义：能否把模糊目标变成 AI 可执行任务。
2. 边界控制：能否定义非目标、文件范围、模块边界和验收标准。
3. 验证闭环：是否使用测试、构建、lint、截图、diff review 或人工验收确认结果。
4. 架构判断：是否能判断模块边界、数据模型、权限、安全、重构和系统演进。
5. 系统归属：是否理解关键路径，能为上线、维护、回滚和结果负责。
6. 方法复制：是否把个人方法沉淀成团队可复用的 rules、skill、workflow、playbook 或评测。

## 三、先封顶

先找最高上限，不要先加分。

- 只有代码片段：最高一品。
- 有 demo，但没有验证：最高二品。
- 能交付功能，但主要靠反复修 bug：最高三品。
- 有目标和验收，但缺少架构判断：最高四品。
- 有架构判断，但缺少稳定验证闭环：最高五品。
- 有闭环，但系统归属证据不强：最高六品。
- 个人系统归属稳定，但没有团队复用证据：最高七品。
- 有团队复用证据，但没有公开范式影响：最高八品。
- 有公开范式影响，才可能九品。
- 单条记录或单次会话不能直接判六品以上；高段位需要跨多次会话、多个项目或多个证据类型反复成立。
- 如果高段位证据主要来自 assistant、tool result、progress 或 reasoning，而不是 user 的主动指令，要降级或降低置信度。
- 如果 `user_control_ratio` 很低，要按封顶处理：七品通常不低于 0.08，六品通常不低于 0.03。大量助手自述“已测试、已构建、已完成”不能替代用户主动拥有系统。
- 如果 `promotion_user_decision_ratio` 很低，要按封顶处理：七品通常不低于 0.08，六品通常不低于 0.03。普通指令不能替代系统级决策。

## 四、再定段位

同一段位至少需要两类强证据互相支撑。比如五品不能只靠“架构”一类证据，通常还要看到验证、边界或产品目标。

八品判定必须回答：

- 这个方法是否被别人用过？
- 是否形成团队级资产，而不是个人笔记？
- 是否有复用结果，例如模板、规则库、培训、评测、团队报告或协作规范？

九品判定必须回答：

- 是否创造了公开概念、框架、产品或社区实践？
- 是否影响他人重新理解人与 AI 的协作方式？
- 证据是否来自公开材料，而不是私有会话自述？

## 五、报告写法

报告必须直接、中文、可解释：

- 先说当前段位。
- 再说最强证据链。
- 再说为什么被封顶。
- 最后给下一品升级路线。

如果证据不足，直接说证据不足。不要用模糊词把低置信度包装成高段位。
